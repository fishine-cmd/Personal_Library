## 第一部分：新成员第一次加入要做的事

新加入的开发者按这份清单走完，就能跑起来 + 提交第一次代码。

### 1.1 接受邀请

1. 收到邀请邮件 → 点链接
2. 或者直接打开 https://github.com/fishine-cmd/Personal_Library/invitations
3. 点击 **Accept invitation**

### 1.2 安装必要工具

| 工具 | 用途 | 下载 |
|------|------|------|
| Git | 版本控制 | https://git-scm.com/download/win |
| Python 3.10-3.13 | 跑后端 | https://www.python.org/downloads/ |
| MySQL 8.x | 数据库 | https://dev.mysql.com/downloads/installer/ |
| VS Code 或 PyCharm | 编辑器 | 任选 |

### 1.3 配置 git 身份

只需配置一次：
```bash
git config --global user.name "你的GitHub用户名"
git config --global user.email "你的GitHub邮箱"
```
> 不想暴露真实邮箱可以用 GitHub 的 noreply 邮箱：到 https://github.com/settings/emails 找你的 `<id>+<username>@users.noreply.github.com`。

### 1.4 克隆仓库到本地

选一个目录（比如 `D:\projects\`）：
```bash
cd D:\projects
git clone https://github.com/fishine-cmd/Personal_Library.git
cd Personal_Library
```
> 第一次推送时会要求登录。用 **HTTPS + Personal Access Token (PAT)** 最简单：
> 1. 到 https://github.com/settings/tokens 生成 token（勾 `repo` 权限）
> 2. 推送时用户名填 GitHub 账号，密码填 token

### 1.5 准备 Python 环境

```bash
# 创建虚拟环境（隔离依赖）
python -m venv .venv

# 激活（Windows PowerShell）
.\.venv\Scripts\Activate.ps1
# 如果遇到执行策略报错：
#   PowerShell（管理员）执行一次：Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

# 激活后命令行前面应该出现 (.venv)

# 安装依赖
pip install -r requirements.txt
```

### 1.6 准备数据库

#### MySQL 服务正常启动
1. Windows 服务里看 `MySQL80` 是否 Running
2. 用任何客户端（HeidiSQL / DBeaver / mysql CLI）能连上即可

#### 创建数据库
```sql
CREATE DATABASE library_system CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

### 1.7 配置 .env

```bash
# 把示例文件复制成实际配置文件
cp .env.example .env
# Windows PowerShell:
copy .env.example .env
```
然后用编辑器打开 `.env`，填入你本地的：
```
FLASK_SECRET_KEY=换成一段随机字符串（任意32位以上字符就行，开发用）
DATABASE_URL=mysql+pymysql://root:你的MySQL密码@localhost:3306/library_system?charset=utf8mb4
UPLOAD_FOLDER=uploads
MAX_CONTENT_LENGTH=52428800
```

> ⚠️ **`.env` 永远不要 commit**。`.gitignore` 已经帮你拦住了。

### 1.8 运行launch.bat

双击运行弹出两个窗口
浏览器打开 http://127.0.0.1:5000/，看到登录页就 OK。

### 1.9 跑测试（确认环境干净）

```bash
pytest
```
应该看到所有测试通过（绿色）。

### 1.10 完成！准备开始写代码

## 第二部分：日常开发标准流程

 **每次写新功能、修 bug 时都要走的流程**。

### 一图概览

```
1. 同步 main          → git checkout main && git pull
2. 开 feature 分支    → git checkout -b feat/xxx
3. 改代码 → 提交      → 多次 commit
4. 推到远端           → git push -u origin feat/xxx
5. 发 PR              → 在 GitHub 页面上点 "Compare & pull request"
6. 等评审 → 改 → 推   → 直到所有 reviewer 同意
7. 合并到 main        → 在 GitHub 上点 "Merge pull request"
8. 删本地分支         → git branch -d feat/xxx
9. 同步 main 准备下一轮
```

### 2.1 准备阶段：同步 main

**每次开新任务前都要做这一步**，确保你的 main 和 GitHub 上一致。
```bash
git checkout main          # 切回 main 分支
git pull                   # 拉最新
```

### 2.2 创建 feature 分支

分支命名约定（详见第四部分）：
```bash
git checkout -b feat/add-export-csv      # 新功能
git checkout -b fix/login-redirect       # 修 bug
git checkout -b refactor/documents-blueprint   # 重构
git checkout -b docs/update-readme       # 文档
```

### 2.3 在分支上开发

按平时方式改代码、加测试。**频繁 commit**，每个 commit 表示一件可描述的事：

```bash
# 改了几个文件
git status                              # 看变更
git diff                                # 看具体改了什么
git add app/blueprints/documents.py     # 明确加文件
git commit -m "feat: 新增 CSV 导出按钮"

# 又改了别的
git add app/services/export.py tests/test_export.py
git commit -m "feat: 实现 CSV 导出服务和测试"
```

> 💡 **不要把无关的改动塞一个 commit**。"加导出功能 + 修拼写错误"应该是两个 commit。

### 2.4 推到远端

第一次推这个分支：
```bash
git push -u origin feat/add-export-csv
```
后续在这个分支上的 push：
```bash
git push
```

### 2.5 发 Pull Request

#### 在 GitHub 网页上
1. 打开仓库主页，会看到顶部黄色提示条 **"feat/add-export-csv had recent pushes... Compare & pull request"** → 点它
2. 或者点 **Pull requests** → **New pull request** → 选你的分支

#### 填写 PR
- **Title**：和你 commit 风格一致，例如 `feat: 新增 CSV 导出功能`
- **Description**（描述清楚做了什么、为什么做、怎么测）：
  ```markdown
  ## 做了什么
  - 在文献列表页加"导出 CSV"按钮
  - 新增 services/export.py 模块封装导出逻辑
  
  ## 为什么
  - 用户反馈想把数据导到 Excel 分析
  
  ## 怎么测
  - 跑 `pytest tests/test_export.py`
  - 手动：列表页 → 点"导出 CSV" → 下载文件 → Excel 打开看
  
  ## Screenshot
  （贴图）
  ```
- **Reviewers**：右侧选一个或多个队友
- 点 **Create pull request**

### 2.6 等评审 + 改 + 推

评审者会在 PR 页面上：
- 留下评论 / 提建议
- 直接在某行代码上批注
- 提交 **Approve**、**Request changes** 或 **Comment**

**收到 Request changes 时**：
```bash
# 在同一个分支上改代码
git add <file>
git commit -m "fix: 按 reviewer 建议调整字段名"
git push                # 不需要 -u，已经追踪过了
```
PR 会自动更新，reviewer 会看到新提交。

### 2.7 合并到 main

所有评审者点了 **Approve** 后，PR 上会出现绿色 **Merge pull request** 按钮：

合并方式三选一（仓库默认通常是 Merge commit）：

| 方式 | 效果 | 推荐场景 |
|------|------|----------|
| **Merge commit** | 保留所有 commit，加一个 merge commit | 想完整保留开发过程（默认） |
| **Squash and merge** | 把分支上的所有 commit 压成一个 | feature 内部 commit 比较乱 |
| **Rebase and merge** | 把所有 commit 线性叠到 main，无 merge commit | 想要漂亮的线性历史 |

**对新手推荐 Squash**：一个 PR = 一个 commit，main 历史更干净。

点 **Confirm merge** 后，建议立即点 **Delete branch**（远端分支也清掉）。

### 2.8 同步本地、清理分支

```bash
git checkout main           # 切回 main
git pull                    # 拉合并后的最新
git branch -d feat/add-export-csv     # 删本地的 feature 分支
git fetch --prune           # 清理远端已删除的分支引用
```

## 第三部分：常见场景与故障排查

### 3.1 我改了文件还没 commit，想撤销改动

```bash
git checkout -- path/to/file       # 撤销单个文件的未提交改动
git checkout -- .                  # 撤销所有未提交改动（谨慎！）
```

### 3.2 我 commit 了但还没 push，想改 commit 信息

```bash
git commit --amend -m "新的信息"     # 改最近一次 commit
```

### 3.3 我 push 了 PR 分支但发现少改一个文件

```bash
git add forgotten_file.py
git commit -m "fix: 补上漏掉的文件"
git push
```
PR 会自动更新。

### 3.4 main 上有人合了新代码，我的分支落后了

#### 方式 A：rebase（推荐，保持线性历史）
```bash
git checkout main && git pull           # 先同步 main
git checkout feat/my-branch             # 切回你的分支
git rebase main                         # 把你的 commit 重新叠到最新 main 上
# 如果有冲突 → 改文件 → git add → git rebase --continue
git push --force-with-lease             # rebase 改了历史，必须强推
```

#### 方式 B：merge main 进来（保留分叉痕迹）
```bash
git checkout feat/my-branch
git merge main
# 解决冲突 → git add → git commit
git push
```

**推荐 A**：历史更清晰。但记住强推用 `--force-with-lease` 不要用 `--force`。

### 3.5 冲突怎么解决

`git rebase` 或 `git merge` 时出现 `CONFLICT`：

```bash
git status        # 看哪些文件冲突
```
打开冲突文件，会看到：
```python
<<<<<<< HEAD
你这边的版本
=======
对方的版本
>>>>>>> origin/main
```
手动编辑保留你想要的部分，删除冲突标记，然后：
```bash
git add 解决了的文件.py
git rebase --continue       # 如果是 rebase
# 或
git commit                  # 如果是 merge
```

> 💡 **复杂冲突先停下来沟通**。冲突说明两个人改了同一处代码，先在 Slack/微信问清楚对方的本意，再决定怎么合。

### 3.6 我 push 错了分支 / push 了不该推的内容

不要慌，几乎所有事都能撤回。

**push 了一个 commit 想撤回（已被别人拉过）**：
```bash
git revert <commit-hash>    # 生成一个反向 commit
git push
```

**push 了密钥/密码（!!紧急!!）**：
1. 立刻**重新生成那个密钥**（让旧的失效）
2. 然后再考虑清理历史
3. 不要花时间纠结"删了就好了"——GitHub 早被爬虫抓过

### 3.7 git pull 失败 "Your local changes would be overwritten"

意思是你本地有未提交改动，pull 会覆盖它们。先处理本地：
```bash
git stash             # 把本地改动暂存
git pull
git stash pop         # 拿回暂存的改动
```

### 3.8 我不小心 commit 到 main 分支了（分支保护会拦你 push）

```bash
git branch feat/should-be-here       # 给当前位置取个分支名
git reset --hard origin/main         # main 回退到远端
git checkout feat/should-be-here     # 切到新分支继续 push
```

### 3.9 .env 不小心被 commit 了（还没 push）

```bash
git rm --cached .env                 # 从 git 移除但保留本地文件
git commit --amend                   # 改写上一个 commit
```
如果已经 push 出去：**立刻重新生成 SECRET_KEY 和数据库密码**。

## 第四部分：提交规范与命名约定

统一规范让 PR 评审、commit 历史、分支列表都更易读。

### 4.1 分支命名

| 前缀 | 用途 | 例子 |
|------|------|------|
| `feat/` | 新功能 | `feat/add-csv-export` |
| `fix/` | 修 bug | `fix/login-redirect-loop` |
| `refactor/` | 重构（不改行为） | `refactor/split-documents-blueprint` |
| `docs/` | 仅文档 | `docs/update-readme-install` |
| `test/` | 仅测试 | `test/add-bibtex-edge-cases` |
| `chore/` | 杂项（依赖、配置等） | `chore/bump-flask-version` |

格式：**`类型/短描述-用连字符`**，全小写英文。

### 4.2 Commit Message 规范（Conventional Commits）

格式：`<类型>: <简短描述（中文/英文均可）>`

```
feat: 新增 CSV 导出按钮
fix: 修复登录后跳转到错误页
refactor: 把 documents.py 的表单逻辑抽到 services
docs: 在 README 加快速上手段落
test: 补充 BibTeX 解析的边界用例
chore: 升级 Flask 到 3.0
```

#### 较大改动用多行 message
```
feat: 实现文献批量导入

- 支持 .bib 和 .ris 两种格式
- 重复项默认跳过，可选择覆盖
- 加进度条显示导入进度

Closes #42
```

### 4.3 PR 描述的好习惯

每个 PR 都说清楚：
1. **做了什么**（What）
2. **为什么这样做**（Why）—— 最重要
3. **怎么测**（How to test）
4. **截图**（如果是 UI 改动）
5. **关联 Issue**（写 `Closes #N` 让合并时自动关闭 issue）

### 4.4 代码改动原则

- **一个 PR 只做一件事**。"加功能 + 顺手重构" 拆成两个 PR
- **改动尽量小**。大 PR 评审起来痛苦
- **加新功能必须加测试**
- **提交前先自测一遍**，别让 reviewer 当 QA
- **看到不相关的代码问题 → 开个 issue，别顺手改**

## 附录：常用命令速查表

### 日常 95% 命令

```bash
# 看状态
git status                      # 当前有什么变更
git log --oneline -10           # 最近 10 个 commit
git diff                        # 未暂存的改动
git diff --staged               # 已暂存的改动
git branch                      # 本地所有分支

# 同步
git pull                        # 拉远端最新
git fetch --prune               # 只拉信息，并清理远端已删的分支

# 分支
git checkout main               # 切到 main
git checkout -b feat/new        # 创建并切到新分支
git branch -d feat/old          # 删本地分支
git push -u origin feat/new     # 第一次推新分支
git push                        # 后续推送

# 提交
git add <file>                  # 暂存
git commit -m "..."             # 提交
git commit --amend              # 改最近一次 commit

# 撤销
git checkout -- <file>          # 撤销未暂存改动
git restore --staged <file>     # 撤销暂存
git revert <hash>               # 反向 commit（已 push 的用这个）
```

### 5% 进阶命令

```bash
# Rebase（保持线性历史）
git rebase main                 # 把当前分支叠到 main 最新
git rebase -i HEAD~5            # 交互式整理最近 5 个 commit
git push --force-with-lease     # rebase 后必须强推（安全的强推）

# Stash（临时存档）
git stash                       # 把当前改动暂存起来
git stash pop                   # 拿回来
git stash list                  # 看暂存了什么

# 查找
git log --all --grep="登录"     # 搜 commit message
git log -S "function_name"      # 搜代码出现/消失
git blame <file>                # 看每行是谁改的

# 远程
git remote -v                   # 看远端地址
git fetch origin                # 只下载，不合并
```

### 不要轻易碰的命令

```bash
git reset --hard <commit>       # 丢弃所有本地改动到指定 commit
git push --force                # 强推（不安全，请用 --force-with-lease）
git clean -fd                   # 删除所有未跟踪文件
```

## 总结：每天的标准动作

```
☐ 开始工作前：git checkout main && git pull
☐ 开新功能/bug：git checkout -b feat/xxx
☐ 多次 commit：写一点 → 测一下 → git add → git commit
☐ 完成后：git push -u origin feat/xxx
☐ GitHub 上发 PR，写清楚 What/Why/Test
☐ 等评审，根据反馈改 → push
☐ 通过后 Squash and merge → Delete branch
☐ 本地：git checkout main && git pull && git branch -d feat/xxx
```

---

> **遇到没把握的操作不要硬来**：尤其是 `git reset --hard`、`git push --force`、`git rebase` 等会改写历史的命令。先在群里问、或者自己开个练习分支试，确认效果再来主分支操作。
